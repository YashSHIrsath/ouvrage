# CODING_STANDARDS.md

# Purpose

This document defines coding standards for the entire application.

All code generated by Claude must follow these rules.

Code quality is more important than development speed.

---

# General Principles

Priorities:

1. Readability
2. Maintainability
3. Reusability
4. Simplicity
5. Performance

Avoid unnecessary complexity.

---

# TypeScript Rules

* Use strict TypeScript.
* Avoid `any`.
* Prefer interfaces.
* Type all props.
* Type all API responses.

Bad:

```ts
const user: any
```

Good:

```ts
interface User {
    id: number;
    name: string;
}
```

---

# React Rules

Use:

* Functional components.
* Hooks.
* Composition.

Do not use:

* Class components.
* Large components.
* Deep prop drilling.

---

# Component Rules

One component = one responsibility.

Maximum:

* 200 lines preferred.
* 300 lines absolute maximum.

If larger:

* Split into smaller components.

---

# Page Rules

Pages should:

* Load data.
* Compose sections.
* Handle routing.

Pages should NOT:

* Contain API calls.
* Contain business logic.
* Contain large forms.

---

# Business Logic

Business logic belongs in:

* services
* hooks
* actions

Never inside:

* pages
* UI components

---

# API Rules

Use:

* React Query
* Service layer

Do not:

```ts
fetch()
axios()
```

inside components.

---

# Form Rules

Always use:

* Shared inputs
* React Hook Form
* Zod validation

Never use Ant inputs directly.

---

# Styling Rules

Allowed:

* Ant Design tokens
* CSS Modules

Not allowed:

* Inline styles
* Hardcoded colors
* Hardcoded spacing

---

# Naming Conventions

Components:

```text
ProjectCard
HeroSection
ThemeSwitcher
```

Hooks:

```text
useProjects
useTheme
```

Stores:

```text
authStore
themeStore
```

Services:

```text
projectService
authService
```

---

# Folder Ownership

Features own:

* API
* Hooks
* Types
* Components

Shared components belong in:

components/

---

# Error Handling

All API operations must support:

* Loading state
* Error state
* Success state

Never silently fail.

---

# Validation

Frontend:

* Zod

Backend:

* Laravel Requests

Validation must exist in both places.

---

# Comments

Comment:

* Complex logic
* Business rules

Do not comment obvious code.

---

# Performance Rules

* Lazy load pages.
* Memoize expensive computations.
* Avoid unnecessary re-renders.
* Optimize images.

---

# Reusability Rules

Before creating:

1. Search existing components.
2. Extend if possible.
3. Create new only if necessary.

Duplicate code is not acceptable.

---

# AI Instructions

Before writing code:

1. Check documentation.
2. Check existing components.
3. Check existing services.
4. Follow design system.
5. Follow folder structure.

The goal is long-term maintainability, not rapid code generation.
# Data Management Rules

Never permanently delete business records.

Use status-based deletion.

Status values:

1 = Active
0 = Inactive
9 = Deleted

Examples:

- Services
- Projects
- Testimonials
- Team Members
- FAQs

Delete operations should:

- Change status to 9.
- Record update timestamps.
- Preserve historical data.

Hard deletes should only be used for:

- Temporary uploads.
- Cache tables.
- System-generated data.

Controllers, services, and repositories should respect status filtering.
